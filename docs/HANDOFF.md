# 직접 지휘하는 3일 설계와 14시간 현장 계획

## 운영 구조

~~~mermaid

  U["여행자 · 영어 화면"] -->|목표와 복귀 약속| S["요청 처리 · 입력 검증"]
  U -->|선택한 문장만| S
  S -->|문장 해석 요청| M["OpenAI · 목표 후보"]
  M -->|사용자가 확인| U
  S --> R["시간·접근·휴관 규칙"]
  D["출처가 있는 장소 목록"] --> R
  R --> A["다음 행동 · 현장 확인 · 복귀"]
  A -->|직원의 안내 반영| U
~~~

서버는 명시적 조건과 카드 목록으로 결과를 다시 계산한다. 브라우저 탭에는 목표, 약속, 사용자 보고만 보관한다. 영어 자유 문장과 GPS, 계정 정보는 브라우저 저장소에 기록하지 않는다. 당일 복귀 시각을 한 번 정하고 새로고침해도 남은 예산이 늘어나지 않는다. 사용자가 동선을 수정하면 이전 이동 확인값은 다시 받는다. 시간 보고에는 서울 시각이 붙는다. 최근 10분을 넘긴 긍정적인 확인은 다시 확인하도록 표시한다. 대기만으로 약속을 이미 넘겼다는 본인의 이전 보고는 새 대기를 입력해 갱신할 수 있다.

### 사람이 맡는 판단

| 일정 | 승민이 직접 정할 일 | Codex에 줄 지시 예 | 다음 단계로 넘어갈 기준 |
|---|---|---|---|
| 설계 1일 | 같은 체험의 필수 조건과 선호 조건을 구분한다. | “내 영어 문장 8개를 분류표로 만들고, 목표가 모호한 행은 나에게 돌려줘.” | 같은 45분 대기에서 사진·무대 촬영의 정답을 본인이 설명할 수 있다. |
| 설계 2일 | 테스트 문장, 모델, 요청당 비용·허용 지연을 정한다. | “선택한 모델 하나로 사용자 확인 전까지의 결과를 비교하고 오류 유형을 정리해.” | 문장별 정답과 모델 답, 응답 지연, 실제 사용량을 나란히 검토한다. 연결 전에는 미측정으로 기록한다. |
| 설계 3일 | 휴관·접근·대기 범위와 발표에서 검증할 약속을 정한다. | “방금 내가 정한 조건 하나만 바꾸고 실패하던 테스트의 전후를 보여줘.” | 변경을 직접 읽고 승인한다. 팀원의 영어 검수, 운영 규정과 현장 데이터 상태를 확인한다. |

권장 도구는 업무마다 고른다. 한 파일 수정·시험은 Codex 한 세션에서 진행한다. 모델은 서비스 설정에서 교체하고 같은 문장표로 비교한다. Paseo는 개인 개발 세션을 데스크톱·모바일에서 직접 보려는 경우에만 써도 된다. 자동 병합·자동 모델 전환은 설정하지 않았다. GitHub Actions는 결과를 반복 검증하고, Vercel은 이미지와 API가 포함된 웹앱을 배포한다. 개발 멘토 검수 표는 정식 참가 또는 외부 지원 범위가 확인된 경우에 사용한다.

### 14시간 현장 추정

24시간 행사 중 실제 작업 시간을 14시간으로 둔 가정이다. 아래 시간은 팀당 경과시간이며 이번 리허설의 사람 작업시간 실측은 아니다.

| 구간 | 구현·검수 작업 | 합격 기준 | 밀리면 |
|---|---|---|---|
| 0~1h | 빈 저장소·환경·규정 확인. 담당자가 목표 두 문장을 직접 확정 | 영어 목표와 약속 값을 손으로 설명 | 버튼을 우선 제공 |
| 1~3h | 공간·운영 출처 재확인, 핵심 규칙과 시간 테스트 작성 | 45분 사례·엄격한 목표·휴관 분기가 서로 다름 | 출처 모순 후보 제외 |
| 3~6h | 입력 화면, 서버 요청, 결과, 직원 한국어 문장 | 전화기 한 대에서 데모 전체 통과 | 장식·추가 지역 축소 |
| 6~8h | 같은 목표 재선택, 전체·부분 휴관, 취소 | 비동기 중복 탭에도 대기 누적 없음 | 최근 한 번의 변경만 복구 |
| 8~9h | 승인된 모델로 영어 메모 해석. 사용자가 확인해야 반영 | 모호한 입력·오류 시 수동 버튼, 키 노출 없음 | 버튼 동작을 유지하고 연결 한계 표시 |
| 9~11h | 운영 환경 키·시간·소스 점검, 통합 테스트, SBOM 확인 | 모바일·새로고침·API 실패 시나리오 통과 | 범위 고정, 실패 사례 재시험 |
| 11~12h | 배포 담당자가 실제 URL·직원 카드·공개 범위를 확인 | 새 브라우저에서 버튼 흐름 성공 | 마지막 정상 빌드로 복구 |
| 12~14h | 한국어 발표, 엄격한 목표와 완화 가능한 목표 비교, 최종 리허설 | 팀원이 두 경우를 1분 내 재현하고 한계를 설명 | 정적 캡처에 촬영 시점과 시연 범위 표시 |

## 재단 인계와 점검

- **기획 담당**은 운영 페이지의 층·운영일·시간·입장 마감·출처·검토일을 비교한다. 여행자가 보고한 대기나 휴관은 해당 탭의 선택에만 반영된다.
- **개발 담당**은 API 키를 서버 환경에 넣고 요금·사용량을 확인한다. 메모 요청 길이는 300자, 대기 제한은 5초, 요청 본문은 14,000바이트다. 인스턴스당 분당 24건의 해석 요청 제한은 분산 환경의 전체 지출 상한을 보장하지 않는다. 일반 공개 운영을 확대할 때 프로젝트 예산 알림·외부 호출 총량을 별도 검증한다.
- **인수 담당**은 Vercel·OpenAI를 재단 소유 계정으로 연결하고 운영자 연락처와 실제 비용을 기록한다. 배포 계정·저장소 주체·모델 공개 범위를 점검한다. 모델은 사실·시간·추천 후보를 쓰지 못하며, 구조화 결과의 열거값만 서버 검증을 통과한다.
- **검수 담당**은 원본 데이터·전체 입력 내용을 서비스 로그에 남기지 않는지 확인한다. 브라우저 원문 저장과 서버 중앙 DB는 사용하지 않는다. OpenAI 호출에는 store=false를 지정한다. 제공자 자체 보존·사용량 처리에는 해당 계정 약관이 적용된다.
- **배포 확인**은 새 브라우저의 데모, 45분 변경, 새로고침, API 오류, 키 없는 버튼 흐름을 점검한다. 빌드 성공과 실제 방문자의 실행 성공을 따로 기록한다.
- **본선 담당**은 리허설 저장소를 현장에 복제하지 않는다. 문서·프롬프트·데이터셋 반입 가능 여부는 재단 확인 사항이다. 현장 소스·최종 프롬프트·매뉴얼·실제 배포물의 SBOM은 현장판에서 새로 정리한다.

## 검증 범위

테스트는 장소 경계, 시간 예산, 휴관 범위, 새 보고가 이전 값을 대체하는 경우, 모호·거절 응답을 확인한다. 실제 브라우저 시험은 데스크톱과 휴대폰 크기, 한국어 질문, 목표 제한, 새로고침, 새 대기로 복구, HTTP 오류를 포함한다. 모델 정상·거절·요청 실패는 테스트 응답을 주입해 재현한다. 현장에서 실제 방문자가 행동을 바꿨는지, 당일 대기, 평균 이동시간과 실모델 정확도는 독립적인 관측이 필요하다.
